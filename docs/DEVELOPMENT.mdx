## Overview

A self-hosted web app that converts a DWG drawing into PNG images:

1. The user uploads a `.dwg` file.
2. The server reads and normalizes the drawing, renders the model space and/or
   every paper-space layout into an SVG, and rasterizes each into a
   white-background PNG — **one PNG per sheet**.
3. The user previews the sheets, selects one, and can download it.
4. Optionally, the server sends the **selected** sheet's PNG to Google Gemini to
   produce a photorealistic architectural visualization. That PNG and the
   configured prompt are the only two inputs.

Design principles:

- **Multi-sheet export.** The app exports every paper-space layout as its own
  sheet (PNG + conversion id), followed by the model-space crops. A DWG with
  more layouts than `MAX_LAYOUTS` (default `100`) is rejected early with
  `MULTIPLE_LAYOUTS` instead of spending minutes rendering. Model crops share
  that budget and are merged down to whatever the layouts leave over.
- **Model space split by drawing.** Model space in a multi-layout DWG holds
  every drawing parked side by side, so it is cut at the widest whitespace gaps
  into separate, tightly-cropped sheets (`Model`, `Model 2`, ...). A gap worth
  less than `MODEL_CLUSTER_GAP_FRACTION` of the overall model size is internal
  detail, so a dense drawing is never shredded.
- **Own renderer.** The SVG is produced by our own renderer from a normalized
  internal model, not by the DWG parser's SVG writer. This decouples
  rasterization from parsing and keeps control of line weights, colors, and
  scaling.
- **Fail safe on the network.** Nothing from a DWG is sent anywhere except the
  (optional, key-gated) Gemini request. Internal error messages never reach the
  browser — only friendly, translated messages keyed by an error code.

## Conversion pipeline

The pipeline is deliberately modular — every stage is a small function with a
narrow contract. Entry points: `frontend/src/server/services/convertDwg.ts`.

### 1. Request handling — `app/api/convert/route.ts`

On every `POST /api/convert`:

1. **Rate limit** — `takeRateLimit(clientIp(request), …)` rejects with
   `RATE_LIMITED` when the per-IP budget is exceeded.
2. **Intake** — `content-type: application/json` selects the direct-upload path
   (`uploadPath` is checked with `isTrustedUploadPath`, then read back and
   measured); anything else is parsed as multipart with a single `file` field,
   converted straight out of the request buffer.
3. **Validation** — extension must be `.dwg` (`validateExtension`) and size
   within `MAX_FILE_SIZE_MB` (`validateFileSize`).
4. **Expired-object sweep** — `sweepExpiredOutputsThrottled` reclaims stale
   `outputs/` and `uploads/` objects (best effort; failures are logged, not
   fatal). This runs *after* intake on purpose: a directly-uploaded DWG is still
   sitting in `uploads/` waiting to be read, and the sweep covers that prefix,
   so sweeping first could delete the file this request is about to convert.
5. **Convert** — calls `convertDwg(buffer, config)`, stores the PNG and a
   `.name` sidecar, returns the JSON result with statistics.
6. **Cleanup** — a staged `uploadPath` is always deleted in a `finally` block.

Sheet names and file names come out of the DWG and may contain control
characters; every value that reaches a log line is escaped by `logSafe` so a
crafted sheet name cannot forge log lines or drive terminal escapes.

`export const maxDuration = 300` (up to 5 minutes) and `runtime = "nodejs"`.

### 2. Orchestration — `convertDwg.ts`

`convertDwg` runs three phases and reports timings for each:

```ts
const inspected = await inspectDwg(arrayBuffer, logger, overrides);
const views = selectViewsForConversion(inspected.views, config.maxLayouts);
const modelEntities = inspected.views.find((v) => v.isModel)?.drawing.entities ?? [];
const { renderable, omitted } = partitionRenderable(views, modelEntities);  // stage 1
const sheets = [];
for (const view of renderable) {
  const output = await renderViewPng(view, config, logger);
  if ((await rasterInkFraction(output.png)) < config.blankSheetInkFraction) {
    omitted.push({ name: view.name, reason: "too-little-detail" });   // stage 2
    continue;                           // never reaches saveOutput()
  }
  sheets.push(output);
}
if (sheets.length === 0) throw new AppError("NO_DRAWABLE_CONTENT", "…");
```

- **Signature check** — `validateDwgSignature` verifies the `AC10` magic bytes
  and the version (`AC1012`…`AC1032` = R13…2018+). Passwords/corruption or an
  unknown version are rejected before any heavy parsing. Note the format has
  not changed since 2018: `AC1032` also covers AutoCAD 2019 through 2027.
- **Parse** — `dwgParser.parseViews` normalizes the model space and every
  paper-space layout into `ParsedView`s. Views are the renderable units; each
  carries its own bounds, page (viewport windows), and statistics.
- **Selection** — `selectViewsForConversion` returns **every** paper-space
  layout view in draw order, followed by the model-space crops. If the renderable
  layout count exceeds `maxLayouts` it throws `MULTIPLE_LAYOUTS`; with no content
  at all it throws `NO_DRAWABLE_CONTENT`. `selectViewForConversion` remains as
  the single-sheet helper (`selectViewsForConversion(...)[0]`).
- **Model clustering** — `expandModelView` turns the single model view into one
  view per drawing cluster via `modelClusterer.clusterModelEntities`, named
  `Model`, `Model 2`, ... The cluster's own bounds flow into `computeViewport`,
  which already fits any bounds to the full canvas, so tight bounds are all the
  zoom that is needed. Clusters beyond the remaining budget are merged into
  their nearest neighbour by `limitClusters` rather than dropped, so capping
  output can only coarsen crops — never lose entities.
- **Render** — each selected view is rendered and rasterized at up to
  `MAX_PNG_DIMENSION` via `renderViewPng`. For very large drawings
  (≥ 15,000 normalized entities) the supersample is disabled
  (`supersampleForEntities`) — a 6000px canvas with tens of thousands of
  entities would otherwise be disproportionately slow.
- **Blank sheets are dropped only when `DROP_BLANK_SHEETS=true`** (off by
  default, so every sheet becomes a PNG and no drawing content can be
  silently lost). When enabled, two stages apply — the rule is *no drawing, no
  PNG*, and each stage catches a failure the other cannot.

  1. **Does the sheet show a drawing?** (`blankSheet.hasSheetDrawing`, run
     *before* rendering, so a rejected sheet costs no pixels). A paper-space
     layout is blank when it has no usable viewport, or when no model geometry
     lands inside any of its viewport windows. Model entities are projected with
     `modelToPagePoint` — which already handles viewport twist — and tested
     against the page rect; entities on a layer in `frozenLayers` are skipped
     because they render as nothing. A model crop is blank when it holds nothing
     but `TEXT`/`MTEXT`/`POINT`. Only `DRAWING_ENTITY_TYPES` (`LINE`, `CIRCLE`,
     `ARC`, `ELLIPSE`, `POLYLINE`, `SOLID`, `IMAGE`) count as a drawing: a note
     or a stray point renders as almost nothing and reads as blank.

     This stage exists because a layout whose viewport frames empty model space
     still renders a *page* full of border, title block and hatch ink, which is
     exactly what a blank sheet looks like. Ink cannot tell the two apart; the
viewport geometry can. The check projects all four bounds corners and
      over-approximates, erring toward keeping a sheet — a false keep leaves a
      blank page, a false drop would lose a real drawing. A prefilter on the
      unrotated model-space bounds keeps the cost negligible.

  2. **Does the render clear the ink threshold?** `rasterInkFraction` measures
     ink coverage on the rendered PNG. A sheet under `blankSheetInkFraction`
     (`BLANK_SHEET_INK_FRACTION`, default 0.005 = half a percent of the page) is
     dropped, catching a sheet that does hold geometry yet still renders nearly
     empty.

  A sheet must pass both (when dropping is enabled). Dropped sheets are recorded in `omittedBlankSheets`
  with a `reason` (`no-drawing` or `too-little-detail`) and **not** returned in
  `sheets`, so they are never rasterized to storage, never downloaded, and never
  offered to the AI step. The UI shows an "N sheets produced no PNGs" note
  listing the names and reasons. The ink threshold is deliberately low so a real
  but sparse plan is kept; the trade-off is that it is fixed at request time, so
  a drawing lost in production is corrected by setting the env var rather than a
  redeploy. If *every* sheet is blank, the conversion is rejected with
  `NO_DRAWABLE_CONTENT` (422) rather than returning an empty result the UI cannot
  render.
- **Two other ways a sheet never becomes a view** — a layout with zero
  entities *and* zero viewports never becomes a view at all:
  `pageFromBlockRecord` (`dwgParser.ts`) returns `null` because there are no
  bounds to compute a viewport from. And a DWG with more layouts than
  `MAX_LAYOUTS` is rejected with `MULTIPLE_LAYOUTS` before any rendering.

### 3. Reading — `dwgReader.ts`

A port seam isolates the whole app from the concrete DWG engine:

```ts
interface RawDwgData { version: string | null; document: CadDocument }
interface DwgReaderPort { read(arrayBuffer: ArrayBuffer): RawDwgData }
```

`AcadDwgReader` wraps `DwgReader.readFromStream` from `@node-projects/acad-ts`.
The engine is created via `createDwgReader()` and is injectable through
`overrides`. Swapping engines later means implementing `DwgReaderPort` only.

### 4. Normalization — `dwgParser.ts` + `entityExtractor.ts`

Parsing converts the acad-ts object graph into the internal `Drawing` model.
Highlights:

- **Entity extraction** (`entityExtractor.ts`) maps acad-ts classes
  (`Line`, `Circle`, `Arc`, `Point`, `Ellipse`, `LwPolyline`, `Polyline*`,
  `TextEntity` (including valued block `ATTRIB` instances), `MText`,
  `Spline`, `Solid`, `Face3D`, `MLine`, `XLine`/`Ray` (stretched to the sheet
  diagonal by `resolveInfiniteLines`), `Tolerance`, `Mesh`/`PolygonMesh`/
  `PolyfaceMesh` faces, ACIS `ModelerGeometry` wire outlines (`Region`,
  `Solid3D`, `CadBody`, AEC `Wall` as a plan rectangle), `TableEntity` grids
  with cell text, `MultiLeader` lines with labels, underlay/OLE placement
  frames, plus `Hatch`/`Dimension`/`Leader` below) into the existing normalized
  types (`LINE`, `POLYLINE`, `TEXT`, `SOLID`, `IMAGE`, `POINT`), so the
  renderer, bounds and viewport projection need no per-class cases. Colors
  resolve to CSS hex; near-white colors become black; layers and visibility
  are resolved eagerly. Legacy `SHAPE` glyphs keep only their insertion point
  (acad-ts exposes no reconstructible outline).
- **Splines** are tessellated into dense polylines via
  `spline.tryPolygonalVertexes(...)` (segment count scales with control-point
  count, clamped to 24…512).
- **INSERT / block expansion** — architectural drawings rely on blocks.
  `normalizeEntity` explodes `Insert` recursively back into world coordinates.
  `MAX_BLOCK_EXPANSION_DEPTH = 16` guards against self-referencing or deeply
  nested blocks that would otherwise blow the call stack. Non-renderable
  sub-entities (`HANDLE`, `SEQEND`, `VERTEX`, …) are skipped silently.
- **Hatches** — solid/plain hatches become one filled polygon per boundary
  loop; pattern hatches are exploded into their line segments (falls back to
  the boundary outline if the explode fails).
- **Dimensions** — the anonymous `*D` block is rendered so extension lines,
  arrowheads, and measured text reproduce what AutoCAD shows. Grip-definition
  `POINT`s are dropped.
- **Leaders** — become a polyline plus an optional filled arrowhead triangle
  sized from the dimension style (with a legibility fallback for tiny or
  unit-mismatched styles).
- **Paper-space views** — each ACAD_LAYOUT layout becomes a `ParsedView`; its
  `Viewport` entities become `PageViewport` windows (with `frozenLayers` and
  rotation). Layouts with no renderable content are skipped. Legacy DWGs with
  no layout table fall back to the single `*Paper_Space` block.
- **Warning aggregation** — the `WarningCollector` collapses the ubiquitous
  "unsupported entity" noise into one line per type with a running count.

Stats are collected per view: `totalEntities`, `renderedEntities`,
`skippedEntities` (unsupported + invisible + failed), plus `page.{entityCount,
viewportCount}` when a paper-space page exists.

### 5. Rendering — `renderer.ts`

The renderer is the only consumer of the `Drawing` model (400-line module,
no acad-ts imports). It emits a plain SVG in **final pixel coordinates**
(Y inverted, margins applied, white background):

- **Two modes** — `renderModelToSvg` fits the raw model bounds;
  `renderPageToSvg` renders the sheet at page proportions with each viewport
  window showing the model content **clipped** to its rectangle. This
  reproduces what AutoCAD shows at "full page size".
- **Z-order** — entities are emitted in fixed passes:
  `POLYLINE → LINE → CIRCLE → ARC → ELLIPSE → SOLID → POINT → TEXT → MTEXT`
  so fills land behind text.
- **Supersampling** — the SVG is emitted at `supersample × target size`, then
  sharp downsamples it (anti-aliasing). `MAX_SUPERSAMPLED_EDGE = 6144` scales
  the supersample back so no canvas edge explodes.
- **Geometry quality** — arcs and ellipses are sampled with an adaptive step
  that keeps chord error at ~0.25 px (`arcStep`); polyline bulges are rebuilt
  into arcs via `arcFromBulge`; ellipse geometry derives the minor axis from
  the major-axis endpoint and `radiusRatio`.
- **Line weights** — `mapLineWeightToPixels` (Raw DWG 1/100 mm → px), floored
  at `MIN_STROKE_PX` so hairlines don't vanish.
- **Text** — rendered as `<text>` with font-size from CAD cap height
  (÷ 0.7 em ratio), rotation, oblique angle and width factor. Multi-line MTEXT
  becomes one `<tspan>` per line at 1.5× pitch, wrapped to the MTEXT rectangle
  width.
- **Text metrics are shared** — `server/services/textMetrics.ts` is the single
  source of truth for how much room a label occupies (per-character advance
  widths, alignment-aware, rotation-aware). `boundsCalculator` and the
  renderer's viewport culler both call `textEntityBounds`. This is load-bearing:
  when the culler sized a label from its **anchor point alone**, any label whose
  anchor sat outside a viewport's model window was dropped even though its glyphs
  were visible inside it — the classic "text is missing" bug. Underestimating
  the same box clips labels at the sheet edge. Alignment is currently fixed to
  left/baseline (see [Known limitations](#known-limitations)).
- **Colors** — monochrome is the default: pure black strokes and black labels on
  white. Substantial filled regions are still painted light grey
  (`MONOCHROME_HIGHLIGHT_FILL`, `#d4d4d4`) so a hatch or a marked-up area reads
  as a highlight instead of collapsing into plain black line work; small filled
  marks stay stroke-only, which is what keeps arrowheads crisp (see
  [Solid fills](#known-limitations)). `COLOR_MODE=color` is opt-in and uses the
  resolved entity colors instead, painting `filled` regions in the DWG's own
  colour at `HIGHLIGHT_FILL_OPACITY`.

### 6. Rasterization — `pngGenerator.ts`

`sharp` rasterizes the SVG with a white `flatten`, `resize({ fit: "inside",
withoutEnlargement: true, kernel: lanczos3 })`, and PNG compression level 4
(a deliberate trade: level 9 costs several seconds per sheet for a few percent of
size on a line drawing that is downloaded once). No unsharp mask is applied so
output stays true to the drawing's line weights.

## Data model

Shared, serializable types with **no acad-ts dependency** below the parser
boundary.

### `Drawing` (`server/models/drawing.ts`)

```ts
interface Drawing {
  bounds: Bounds;
  entities: Entity[];        // normalized model-space entities
  layers: Layer[];
  blocks: Block[];           // empty in practice (blocks consumed by expansion)
  page?: Page;               // present when a paper-space sheet exists
}
```

### `Bounds` (`server/models/bounds.ts`)

`minX, minY, maxX, maxY`; helpers `boundsWidth`, `boundsHeight`,
`boundsAreValid`. Computed by `boundsCalculator.drawingBounds`.

### Entities (`server/models/entity.ts`)

All entities carry `color` (resolved CSS hex), `layer`, `lineWeight`
(DWG 1/100 mm), optional `lineType`, and `sourceType` (original DWG class name
for reporting). Types:

| Type | Fields |
| --- | --- |
| `LINE` | `start`, `end` |
| `CIRCLE` | `center`, `radius` |
| `ARC` | `center`, `radius`, `startAngle`, `endAngle` (radians, CCW) |
| `POINT` | `position` |
| `ELLIPSE` | `center`, `majorAxisEndPoint`, `radiusRatio` (0..1), `startAngle`, `endAngle`, `full` |
| `POLYLINE` | `vertices`, `closed`, `bulges[]` (bulge of segment i→i+1) |
| `TEXT` | `position`, `rotation`, `height`, `text`, `alignment` |
| `MTEXT` | `position`, `rotation`, `height`, `text`, `width`, `alignment` |
| `SOLID` | `vertices` (3 or 4), `filled` — used for SOLID/3DFACE and hatch fills |

`SUPPORTED_ENTITY_TYPES` is the canonical allow-list.

### Page (`server/models/page.ts`)

- `Page { entities, viewports, bounds }` — the sheet itself (border, title
  block, notes) plus viewports and its overall bounds.
- `PageViewport` — the viewport rect on the page (`minX..maxY`), the
  model-space region it shows (`viewCenterX..viewHeight`), rotation `twist`,
  and `frozenLayers` (rendered blank).

### Layer & Block (`server/models/layer.ts`, `block.ts`)

- `Layer { name, visible, color?, lineWeight?, lineType? }`
- `Block { name, entities }`

### Statistics (`server/services/dwgParser.ts`)

```ts
interface ConversionStatistics {
  totalEntities: number;
  renderedEntities: number;   // produced ≥1 normalized entity
  skippedEntities: number;    // total - rendered
  warnings: string[];         // aggregated "Unsupported entity X skipped (n)."
  page?: { entityCount: number; viewportCount: number };
}
```

### Client types (`types/conversion.ts`)

Server responses are typed by `MultiSheetResult` (`originalFileName`,
`sheets: ConversionResult[]`, `sheetCount`, `version`, `durationMs`) and
`AiImageResult` (`conversionId`, `fileName`, `size`, `durationMs`). Each
`ConversionResult` carries its own `conversionId`, `fileName`, `sheetName`
(e.g. "FLOORING LAYOUT"), `statistics`, and `warnings`, so every sheet is a
self-contained download/AI target.

## AI image generation (Gemini)

Optional, gated on `GEMINI_API_KEY` being set. Flow:

1. `POST /api/generate/[id]` — validates the id, the key, the rate limit, and
   that `outputs/{id}.png` exists. The JSON body carries only
   `{ regenerate?: boolean }`; a `prompt` field is accepted and ignored, since
   generation is a pure function of (sheet PNG, fixed prompt).
2. Computes the **AI pair id** — `sha256(sheetId:sha256(viewName):sha256(prompt):sha256(png))`
   in `server/services/aiPairCache.ts`, deliberately without the per-upload
   `conversionId` so a re-upload of the same drawing hits the same pair — and
   reads the pair from Supabase *before* touching the generation budget. A live
   pair (both objects present, `expiresAt > now`) is returned immediately: no
   Gemini call, no budget spent. `regenerate: true` is the only way past it.
3. On a miss, reads the converted PNG and calls `generateDrawingImage` in
   `server/services/geminiImage.ts`:

   - `generateContent` to Gemini 3.1 Flash (`gemini-3.1-flash-image`,
     overridable via `GEMINI_MODEL`), payload is `{ parts: [{ inlineData:
     { mimeType: "image/png", data: <base64> } }, { text: prompt }] }`.
   - The prompt is `config.geminiPrompt`, verbatim. Nothing is appended — not the
     sheet's extracted text, not a caller prompt — so the generation is a pure
     function of its two inputs and the derived cache key is sound.
   - The response is parsed leniently for inline or generated-byte data.
   - A **timeout** (`GEMINI_TIMEOUT_MS`, default 240s) abort maps to a friendly
     `AI_GENERATION_ERROR` ("timed out") instead of a dangling request.

4. Stores `outputs/{id}.ai.png` (+ `.name` sidecar `{base}-ai.png`) and writes
   the AI pair, then returns the metadata.
5. `GET /api/download-ai/[id]` serves the generated PNG (same conventions as
   the regular download, including content-type validation client-side).

The default prompt (`DEFAULT_GEMINI_PROMPT` in `config.ts`) is the
owner-supplied **"Generic Drawing-to-Realistic-Image Prompt"**: Gemini identifies
the space/elevation from the drawing itself and produces a single high-resolution
photorealistic visualization that preserves the drawn design exactly, with **no**
CAD text in the result. It is stored verbatim as prose — it is the specification
of what the generated image must be, not generated text — and is overridable
with `GEMINI_PROMPT`, which wins over the built-in default when set.

The request carries exactly two parts: the selected sheet PNG and that prompt.
Nothing else is collected or sent — the drawing's own TEXT/MTEXT strings are not
extracted, stored, or passed to the model. Adding them would make the output
depend on text that is not part of the pair's identity, which would break cache
reuse.

### The AI image cache

One prefix is long-lived in Supabase, holding exactly two objects per generation:

| Key | Contents |
| --- | --- |
| `ai-outputs/{aiPairId}.ai.png` | the image Gemini returned |
| `ai-outputs/{aiPairId}.meta.json` | identity fields plus `createdAt` / `expiresAt` |

The input PNG is deliberately **not** stored. It already lives at
`outputs/{id}.png`, nothing reads its bytes, and the derived id already commits
to which sheet, prompt and PNG bytes this output belongs to — a second copy
would roughly double cache storage to guard against a half-written pair, which
the image-then-metadata write order already prevents.

`aiPairId` is derived, never random: `sha256(sheetId, viewName, promptHash,
pngHash)`. Every component comes from the drawing's bytes and the configured
prompt, so a byte-identical DWG uploaded again resolves to the same pair and
reuses its image. The per-upload `conversionId` is deliberately **excluded** —
it is a fresh UUID every time, so including it would make every re-upload a miss
and pay for another Gemini call.

`expiresAt` is set to `now + CACHE_AGE_MINUTES` on every write, and
`/api/cleanup` deletes a pair only when its own `expiresAt` has passed — reading
the recorded expiry rather than the storage timestamp, so a pair rewritten
mid-window is not culled early.

If no key is configured, the endpoint returns `AI_NOT_CONFIGURED` (503).

## API reference

All JSON error responses share the shape:

```json
{ "success": false, "error": "<friendly message>" }
```

The `error` string is the **user-facing** message for the mapped code — never
an internal stack trace (see [Errors](#errors--rate-limiting)).

### `GET|POST /api/upload`

A tombstone that answers **404** to both methods. Direct-to-storage upload is
removed: a signed PUT URL is a durable public handle on DWG bytes, and nothing
here needs one. `/api/convert` still accepts a JSON `uploadPath`, so a DWG
staged by an earlier version of this app (or written out of band) can still be
converted; only the minting side is gone.

### `POST /api/convert`

Accepts either:

- `multipart/form-data` with a `file` field (`*.dwg`) — the only path the browser
  uses, and
- JSON `{ uploadPath, fileName }` — naming a DWG already staged in storage.

In the JSON case the size check runs against the bytes actually read back, not
anything the client claimed.

- Runtime: `nodejs`, `maxDuration: 300`.
- Validates: extension, size, DWG signature/version, sheet count, rate limit.
- **200**

```json
{
  "success": true,
  "originalFileName": "floor.dwg",
  "sheetCount": 2,
  "version": "AC1032",
  "durationMs": 7231,
  "sheets": [
    {
      "conversionId": "uuid-1",
      "originalFileName": "floor.dwg",
      "fileName": "floor-CIVIL LAYOUT.png",
      "sheetName": "CIVIL LAYOUT",
      "viewId": "layout",
      "size": 284123,
      "version": "AC1032",
      "statistics": { "totalEntities": 1024, "renderedEntities": 980, "skippedEntities": 44, "warnings": [] },
      "warnings": []
    }
  ]
}
```

- **4xx/5xx** on failure (see error table); any staged upload (`uploadPath`)
  is deleted either way. In multipart mode the temporary disk file is removed
  in `finally`.
- `GET` returns 405 with a hint.

### `POST /api/generate/[id]`

Generates the AI image for an existing sheet conversion. Requires
`GEMINI_API_KEY`.

- Body: optional JSON `{ "regenerate": true }`. The flag bypasses the pair cache
  and spends a generation. A `prompt` field is accepted and **ignored**: the
  prompt is fixed by `GEMINI_PROMPT`, so a per-request one would break the cache
  key without changing what the model receives.
- Validates: id format, key present, rate limit, output file exists.
- **200** → `{ success, conversionId, fileName, size, durationMs,
  generationsUsed, generationsLimit, cached, source, blocked }`. `cached: true`
  (with `source: "cached-pair"`) means the image came from the AI pair cache: no
  Gemini call, no generation consumed, `durationMs: 0`, and `blocked: true` so
  the UI stops offering regeneration.
- The cache is consulted **before** the generation allowance is charged, so a
  re-requested drawing still succeeds after the limit is reached. Otherwise the
  route claims one generation atomically (under a per-conversion lock, so two
  concurrent clicks cannot both slip past the cap) and releases it again if
  Gemini or the save fails — a failed attempt is not billed.
- The claim counter lives in the output store, so it is shared across warm
  instances of the same deployment but **not** across separate deployments or
  after the count object is swept with its output.
- **429** `AI_LIMIT_REACHED` carrying `generationsLimit`, so a client can stop
  offering the button; **503** `AI_NOT_CONFIGURED` when the key is missing;
  **404** `FILE_NOT_FOUND` when the PNG is gone.

### `GET /api/download/[id]`

Serves `{id}.png` as an attachment (`Content-Disposition`, `Content-Type:
image/png`, `Cache-Control: no-store`). The file is **not deleted** on download
so the in-page preview and the PNG button share the URL; the age-based sweep
reclaims it.

### `GET /api/download-ai/[id]`

Serves `{id}.ai.png` with the same semantics; name sidecar defaults to
`dwg-ai-generation.png`.

### `POST /api/tilesview/[id]`

Publishes an already-generated AI image to TilesView and returns the room to
open. Requires `TILESVIEW_APP_KEY` / `TILESVIEW_APP_SECRET`.

- Validates: id format, credentials present, rate limit, `{id}.ai.png` exists —
  so an AI image must be generated first.
- **200** → `{ success, conversionId, customRoomsId, visualizerUrl }`.
- `maxDuration = 60`. The UI opens a blank tab synchronously inside the click
  and navigates it to `visualizerUrl` on success, because user activation often
  expires during the upload and the popup would otherwise be blocked.

### `GET /api/cleanup`

Daily cron target. Sweeps `outputs/` and `uploads/` on their age clocks plus
cached AI images on their own `expiresAt`, and answers `{ success, removed,
aiRemoved }`.

- Requires `Authorization: Bearer $CRON_SECRET`; anything else gets a 401. When
  `CRON_SECRET` is unset the route refuses everyone rather than defaulting open.
- `POST` returns 405. On failure the underlying error is logged but never echoed
  back (it contains file paths and bucket names), and `Retry-After: 3600` is
  set.

## Errors & rate limiting

`server/utils/errors.ts` defines the complete taxonomy; a single mapping each
produces the user message and HTTP status so UI and API never drift.

| Code | HTTP | User message |
| --- | --- | --- |
| `INVALID_FILE` | 400 | The uploaded file could not be read. |
| `UNSUPPORTED_EXTENSION` | 400 | Only DWG files are supported. |
| `FILE_TOO_LARGE` | 400 | File size exceeds the allowed limit. |
| `RATE_LIMITED` | 429 | Too many requests. Please try again shortly. |
| `CORRUPTED_DWG` | 422 | Unable to read DWG file. It may be corrupted or password-protected. |
| `UNSUPPORTED_DWG_VERSION` | 422 | Unsupported DWG version. R13 (AC1012) and newer are supported. |
| `MULTIPLE_LAYOUTS` | 422 | This DWG contains more than one drawing… |
| `PARSER_ERROR` | 422 | The DWG file could not be parsed. |
| `NO_DRAWABLE_CONTENT` | 422 | No drawable content was found in this DWG file. |
| `FILE_NOT_FOUND` | 404 | The requested conversion result no longer exists. |

| `AI_NOT_CONFIGURED` | 503 | AI image generation is not configured on this server. |
| `AI_LIMIT_REACHED` | 429 | You've reached the maximum number of AI image generations for this drawing. |
| `STORAGE_UNAVAILABLE` | 503 | The storage service is temporarily unavailable. Please try again later. |
| `RENDER_ERROR` | 500 | The drawing could not be rendered. |
| `PNG_GENERATION_ERROR` | 500 | The PNG image could not be generated. |
| `AI_GENERATION_ERROR` | 500 | The AI image could not be generated. Please try again. |
| `DOWNLOAD_ERROR` | 500 | The PNG could not be downloaded. |
| `INTERNAL_ERROR` | 500 | Conversion failed. Please try again. |

`toAppError(err)` normalizes anything thrown into an `AppError` by looking at
message keywords ("unsupported"/"version" → `UNSUPPORTED_DWG_VERSION`,
"corrupt"/"magic"/"header" → `CORRUPTED_DWG`, "render"/"svg" →
`RENDER_ERROR`, "gemini"/"ai image" → `AI_GENERATION_ERROR`, …).

Rate limiting is a per-IP **fixed** window (`utils/rateLimit.ts`,
`takeRateLimit(ip, max, windowMs)`), applied to convert and generate. The client
IP comes from `clientIpFrom(headers)`, which trusts `x-vercel-forwarded-for`
first, then the *right-most* `x-forwarded-for` entry (the one a trusted proxy
appended — left-most entries are caller-controlled and ignored so a forged
header cannot mint a fresh bucket per request), then `x-real-ip`. Equivalent
spellings of one address (`::ffff:1.2.3.4` vs `1.2.3.4`) are collapsed to a
single key. The window map is capped at 10,000 entries, evicting the
soonest-to-expire client when full. In-memory state is per instance, so the
effective limit is multiplied by the number of warm instances.

## Storage & file lifecycle

`server/services/supabaseStore.ts` is the only module that talks to the bucket.
`outputStore` and `uploadStore` call it, and fall back to disk when
`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are unset, so local dev needs no
credentials.

- **Why a bucket at all** — a converted PNG has to outlive the single
  `convert` request that produced it: the browser previews it and then calls
  `generate/[id]`, and the download routes re-serve it. Local files die with a
  serverless instance, so production output lives in a **private** Supabase
  Storage bucket, namespaced by prefix:

  ```
  outputs/{id}.png            # converted sheet PNG
           {id}.png.meta      # sourceHash / pngHash / sheetId / viewName
           {id}.png.name      # output filename sidecar (UTF-8)
           {id}.ai.png        # AI result
           {id}.ai.png.name   # AI filename sidecar
           {id}.ai.png.count  # successful generations (generation limit)
  ai-outputs/{aiPairId}.ai.png # the image Gemini returned
  ai-outputs/{aiPairId}.meta.json # identity + createdAt / expiresAt
  uploads/{uuid}.dwg          # staged DWG; deleted right after conversion
  ```

  The prefix split is what lets retention differ per group: `outputs/` lives for
  `CLEANUP_AGE_MINUTES` and `ai-outputs/` for `CACHE_AGE_MINUTES`, while
  `uploads/` exists only for the length of one conversion. Without Supabase
  nothing is persisted at all, so every request costs a Gemini call.

  `outputs/` holds **both** the converted PNG and the generated AI image for the
  same conversion, so a single `CLEANUP_AGE_MINUTES` window covers both. It is
  measured from conversion, not from last download: a sheet fetched on day 29
  is still reclaimed on day 30.

  No sheet PNG is duplicated: it is written once to `outputs/`, and the AI cache
  stores only the image Gemini returned. A re-uploaded DWG is recognised by the
  `sheetId` and `pngHash` in the `{id}.png.meta` sidecar, which together make up
  the AI pair identity.

- **IDs** — `newConversionId()` = `randomUUID()`. `isSafeConversionId` enforces
  the strict UUID pattern on every route that accepts an id, so path traversal
  is impossible. A staged `uploadPath` is additionally checked against
  `uploads/{uuid}.dwg` by `isTrustedUploadPath`.
- **Uploads** — the browser always POSTs multipart to `/api/convert`, so a DWG
  is bounded by the platform's request-body limit (~4.5 MB), not by
  `MAX_FILE_SIZE_MB`. The signed-URL path that used to bypass it is removed.
- **On disk** (no Supabase credentials), under `TEMP_DIR`:

  ```
  temp/outputs/{id}.png (+ .meta / .name / .ai.png / .ai.png.name / .ai.png.count)
  ```

  There is no `uploads/` dir: the multipart path converts straight out of the
  request buffer and never stages the file.

- **Atomic writes** — `writeBufferFileAtomic` writes to a unique sibling
  `*.tmp` and `rename`s over the destination, so a concurrent download can
  never observe a partial file.
- **Sweep** — buckets are swept by prefix: `fileCleanup.sweepTempDirs` on disk,
  and `list` + batched `remove` against the bucket when Supabase is enabled.
  Keys are collected in a read-only pass *before* anything is deleted, because
Supabase pages `list` by offset and deleting mid-scan would skip live objects.
  The `ai-outputs/` pairs are swept by `sweepExpiredAiPairs`, which reads each
  pair's own recorded `expiresAt` rather than the storage timestamp.
  Invoked opportunistically from the convert, generate, and download routes
  (throttled to at most once per 10 minutes per process) and, unconditionally,
  by the daily cron. Each route runs the sweep only after it has read whatever
  object it is about to use, so the sweep cannot delete the object the request
  is working on.
`GET /api/cleanup` is the single cleanup entrypoint for the project: it sweeps
   `outputs/`, `ai-outputs/` and orphaned `uploads/` in one pass, and refuses to
   run without the `CRON_SECRET` bearer token. There is no separate CLI
   entrypoint — a second sweeper would need its own copy of the retention
   windows and would drift, which is how the AI cache came to be missed by an
   older manual script.
- **Size limits** — `MAX_FILE_SIZE_MB` is enforced by `/api/convert` against the
  bytes it reads, and a `413` from the platform is reported as such. In practice
  the platform's request-body cap (~4.5 MB) bites first, so a DWG larger than
  that cannot be converted at all while the direct-upload path is gone.

## Verifying conversion fidelity

Set `AUDIT_TEXT=1` to make every conversion log a per-sheet text-fidelity report
alongside the usual progress lines:

```
Text audit "ELEVATION AA (2)": 103/103 strings (100.0%), minCap=12.30px, belowFloor=0, invalid=0 -> PASS
```

Each line answers three questions that eyeballing a PNG cannot separate:

- **coverage** — how many of the strings the sheet is supposed to show reached
  the SVG, and which are missing (named explicitly);
- **`belowFloor`** — labels emitted under `MIN_TEXT_CAP_PX`, i.e. present in the
  vector output but effectively invisible in the raster;
- **`invalid`** — labels with non-finite geometry (`x="NaN"`), which rasterizers
  skip silently, leaving a sheet that looks blank of text while containing every
  right string.

`FAIL` on any of coverage, `belowFloor` or `invalid` means the sheet is not
faithful and the missing strings are listed.

### What "faithful" is verified to mean

Measured on a real 3.3 MB architectural DWG (26 paper-space layouts, 314,838
normalized entities, 1,867 text entities, model extent ~120,000 units):

| Property | Result |
| --- | --- |
| Text anchored on its true DWG coordinate | 1,867 / 1,867 |
| Text inside model bounds | 1,866 / 1,867 |
| Sheets at 100% string coverage | 28 / 28 (2,365 / 2,365 strings) |
| Labels below the legibility floor | 0 |
| Labels with non-finite geometry | 0 |
| Layouts kept by the blank-sheet filter | 26 / 26 |
| Same DWG converted twice → identical PNG bytes | yes |

Determinism matters beyond fidelity: the AI pair cache is keyed on the sha256 of
the converted PNG, so byte-identical output is what lets a re-uploaded DWG reuse
its previous AI image instead of paying for another generation.

### Label size: the one deliberate deviation

Labels are drawn at `max(true size, MIN_TEXT_CAP_PX)`. That floor is **not**
present in the DWG, and on a large drawing it is a substantial distortion — it
exists because the alternative is worse. Annotation is millimetres tall: on a
drawing whose model crop spans ~63,000 units, the median label is 3 units, which
is **0.15px at 3000px**. Rendered at true size it is sub-pixel — present in the
SVG, invisible in the PNG. No practical canvas fixes that (4px honestly would
need ~84,000px), so the floor trades exact relative sizing for legibility.

Measured inflation per view class, with model crops at `MODEL_PNG_DIMENSION=6000`
and layouts at `MAX_PNG_DIMENSION=3000`:

| View | Labels | Median inflation | Notes |
| --- | --- | --- | --- |
| 26 paper-space layouts | 12–16 each | **1.00x** | Floor never binds; already true DWG scale, nothing added |
| `FLOORING LAYOUT 1 (3)` | 16 | 1.00x | One label floored (worst case 3.85x) |
| Whole-model crop | 31 | ~13x | Every label sub-pixel; the only genuinely distorted view |

The layout figures are the important ones: for the sheets a person actually reads,
output is at true scale. Only the whole-model crop is inflated, and AutoCAD shows
no readable text at that zoom either.

Note the floor also flattens the text *hierarchy* on a model crop — in the DWG
those 31 labels span a 125x size range, and after the floor they are all identical.
Raising `MODEL_PNG_DIMENSION` is the only thing that reduces it.

### Label size: the ceiling, and oversized dimensions

The floor is off by default (`STRICT_TEXT_SCALE=true`), which removes the
inflation but leaves text sized purely as `entity.height × viewport.scale` — and
`viewport.scale` is unbounded above, because a small sheet produces a large scale.
Nothing upstream bounded `entity.height` either. Two gaps followed.

**Dimension text.** A dimension's measured value lives in its anonymous `*D` block,
which `expandDimensionBlock` flattens into ordinary `TEXT`/`MTEXT`. That MTEXT
sometimes stores a height of `0`, and `textEntityHeight` then fell through to
`DEFAULT_TEXT_HEIGHT` — `1` unit. acad-ts's own default dimension text height is
`0.18`, so the fallback was ~5.5x too big: on a 36-unit sheet at 3000px, ~115px of
type where a real annotation is 8px. The dimension's style knows the intended size,
so `dimensionStyleTextHeight` reads `textHeight × scaleFactor` off
`getActiveDimensionStyle()` (scaled like `extractLeader` scales arrow size) and
`textEntityHeight` prefers it over the generic default. Text style heights still win
when the entity has one; the dimension style is only consulted when neither the
entity nor its text style is usable.

**The ceiling.** Anything with a genuinely bad height still needs a bound, since
`STRICT_TEXT_SCALE` cannot supply one. `MAX_TEXT_CAP_PX` (default `48`) caps cap
height in both modes: `clamp(true size, MIN_TEXT_CAP_PX, MAX_TEXT_CAP_PX)`. 48px of
cap height (~69px font) sits far above any label genuinely part of a drawing —
title blocks and section marks are the largest — so correct text is untouched and
only a runaway is clamped. Raise it if a drawing has labels larger than that; set
it very high to disable.

The two settings bound opposite ends of the same problem and neither is sufficient
alone: strict mode has no floor, so it needs the cap; non-strict mode has no cap,
so it needs the floor.

### What is *not* claimed

Conversion is geometrically faithful for everything the parser can resolve, but it
is not a pixel-for-pixel match with AutoCAD's plot output — see
[Known limitations](#known-limitations) for the specific gaps (sub-pixel hairlines,
substituted SHX glyphs, unresolved XREFs, OLE/underlay frames).

---

- **Model crops share the layout budget** — layouts are emitted first, and the
  model crops get whatever slots remain under `MAX_LAYOUTS` (default 100). A DWG
  whose layouts alone fill the budget therefore exports no model crop; DWGs with
  more layouts than `MAX_LAYOUTS` are rejected instead of rendering unbounded
  sheets. Rendering runs sequentially inside the route's 300s budget.
- **Clustering is scale-relative** — gaps are measured against the whole model
  size, which keeps a dense drawing intact but means an extreme outlier
  (a stray note orders of magnitude away) can inflate the reference size and
  mask the real gaps between drawings.
- **Text anchoring** — `textAlignment` in `entityExtractor.ts` maps the CAD
  horizontal/vertical alignment flags (and `TextEntity.horizontalMode` /
  `verticalMode` for `TEXT`, the attachment point for `MTEXT`). AutoCAD stores
  the anchor in `alignmentPoint` only when the text is not left/baseline aligned,
  so `textPosition` prefers it and falls back to the group-10 `insertPoint`.
  `alignmentPoint` is honoured **only when it holds a real coordinate**: `acad-ts`
  does not read that field from the DWG and leaves a unit *direction* vector there
  instead — across the 1,867 text entities of a real architectural drawing every
  value had magnitude 1 (`(1,0)`, `(0,1)`, `(0,-1)`, and rotations such as
  `(0.99998, 0.00473)`). Trusting it drew all 817 dimension values plus every
  centred label at the origin, ~100,000 units from the geometry they annotate,
  which is what made dimension text read as missing. `isUnusableAlignmentPoint`
  rejects unit-magnitude points so those labels fall back to `insertPoint`.
  One caveat remains: the vertical anchor is applied as a fixed baseline shift in
  the SVG (cap- and x-height fractions of the font size) instead of a true
  text-box fit. Text extents are measured from real per-character advance widths
  shared by the bounds calculator and the viewport culler (`textMetrics.ts`), but
  the CAD text **font itself** is substituted: a `romans.shx`/`txt.shx` label is
  drawn in a generic sans, so letterforms and exact string widths differ from
  AutoCAD.
- **Not pixel-identical to AutoCAD** — `acad-ts` is a partial DWG reader, so
  output is *geometrically equivalent with all resolvable text present*, not
  pixel-parity. Known gaps: no SHX/TTF CAD fonts, XREF/external block references
  are not resolved (their content is absent from the output), OLE objects and
  underlays render as frames rather than their embedded raster, annotative
  scaling is not evaluated, and AutoCAD's own plot drivers/styling differ again.
  Anything unresolvable is reported as a conversion warning rather than dropped
  silently. Reaching true parity means changing engine (Autodesk APS Model
  Derivative or ODA Drawings SDK), not changing this code.
- **DWG versions** — R13 (`AC1012`) through `AC1032` are accepted. `AC1032`
  is the version used by AutoCAD 2018 and every release since, so it covers
  current AutoCAD too. Pre-R13 files fail signature/version validation, and
  would fail in the parser anyway: `acad-ts` throws `CadNotSupportedException`
  for `AC1002`–`AC1009`.
- **Unsupported entity types** are counted and reported as warnings rather than
  rendered (see `SUPPORTED_ENTITY_TYPES`). Notable: splines are tessellated to
  polylines (faithful, but heavy).
- **Blocks table** — named blocks are not pre-normalized; only inserted block
  instances are expanded (avoids wasting CPU on never-inserted definitions).
- **Solid fills** — a `SOLID`/`3DFACE` polygon, an expanded solid hatch and a
  leader arrowhead all record the DWG's fill intent in `Entity.filled`. In
  **monochrome** a `filled` region is painted light grey
  (`MONOCHROME_HIGHLIGHT_FILL`, `#d4d4d4`) when it covers at least
  `MONOCHROME_HIGHLIGHT_MIN_AREA_FRACTION` (0.05%) of the drawing's own bounds,
  and stroked in black otherwise. Reusing the stroke colour as the fill forced
  `#000000` (and `resolveColorHex` rewrites near-white to black as well), so one
  large filled region painted over a third of the sheet and buried the line work
  — `Fluting sample display (2)` measured 33.8% ink coverage before, 15.3% after.
  The area threshold is what excludes arrowheads: they are `filled` `SOLID`s too,
  but a fraction of a percent of a sheet, and grey-filling them put a blob next to
  every dimension. Measuring against the drawing's bounds rather than an absolute
  unit area keeps the threshold meaningful on a 36-unit sheet and a 4,000-unit site
  plan alike. In **color mode** (`COLOR_MODE=color`) the DWG's own colour is kept
  and every `filled` region is painted at `HIGHLIGHT_FILL_OPACITY` (0.2), which
  is what makes a highlight legible without letting the fill bury the line work.
  Light-grey fill departs from AutoCAD, whose default `monochrome.ctb` plots
  solid hatches as solid black.
- **Color extremes** — near-white colors resolve to black for stroke
  visibility on the white background. This applies to strokes only, never to
  fills.
- **AI image** — requires a configured `GEMINI_API_KEY`; generation is
  time-boxed at 240 seconds server-side (`GEMINI_TIMEOUT_MS`).
- **Per-instance state** — rate-limit windows and the in-flight AI generation
  claim locks live in process memory. On a multi-instance deployment the
  effective per-IP limit and the generation limit are therefore per instance
  (a shared store would be needed to enforce them globally).
